# Release bundle — 2026-08-11 (17:40)

Supersedes `iis-full-20260809-2055`. Deploy this one.

## What changed since the 2055 bundle

One configuration file: `appsettings.Development.json` now sets `SendGrid:Enabled = false`.

**This changes nothing in production** — that file is only read when `ASPNETCORE_ENVIRONMENT` is
`Development`. It fixes local development, where the API had started dialling SendGrid for every
registration and the generated credentials were neither delivered nor written to the console, so a
developer could register an order and never be able to sign in as it.

Application binaries are otherwise unchanged. `api\` still deliberately ships **without** a
`web.config` so a deploy cannot overwrite the one holding your server's secrets.

---

## What this release contains

- **Reveal an order's password** — `GET /api/v1/admin/orders/{orderId}/password`, gated on the new
  `Orders.ViewPassword` permission. Registration now also stores the generated password encrypted,
  alongside the existing hash. **Orders created before this release have nothing to reveal.**
- **SendGrid API key managed from the admin panel** — new **Settings** page (`/settings`), gated on
  `Settings.View` / `Settings.Update`. Stored encrypted in `SiteSettings`, read per send, so
  rotating it needs no redeploy.
- **Schema**: one new nullable column, `Orders.PasswordSecret`.

---

## 🔴 Required setting

Both new features need an encryption key. Without it the platform runs normally, but passwords
cannot be revealed and the Settings page disables itself with an amber banner — which is exactly
the state the panel is in today.

Generate one:

```powershell
$b = New-Object byte[] 32
[System.Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b)
[Convert]::ToBase64String($b)
```

Put it in **either** place — `web.config` wins if both are set:

| Where | Notes |
| --- | --- |
| `api\web.config` → `<environmentVariable name="Security__EncryptionKey" value="…" />` | Matches the existing deployment guide |
| `api\appsettings.Production.json` → `"Security": { "EncryptionKey": "…" }` | **Recommended.** Not in the repo, never generated by publish, excluded by the robocopy line below, so it survives every update. Template in `templates\`. |

Verified: with a bare `web.config` and no environment variable, the key in
`appsettings.Production.json` alone is enough — the endpoint returns `canEdit: true`.

**Back the value up** somewhere other than the server. Change it later and everything encrypted
under it becomes unreadable: the stored SendGrid key must be re-entered, and order passwords saved
under it can never be revealed.

### While you are in that file

If your API `web.config` was overwritten by an earlier deploy, these went with it and are worth
restoring at the same time:

- **`Jwt__SigningKey`** — urgent. Without an override the API signs tokens with the placeholder
  committed to the repository, so anyone who can read the repo can forge an admin token.
- **`Storage__RootPath`** — without it, uploads are written inside the published site folder and
  the next `/MIR` deploy deletes them.
- `Cors__AllowedOrigins__N`, `App__WebUrl`, `App__AdminUrl`.

## Order of operations

Schema first, then the API, then the SPAs. The new API needs the new column; the old API tolerates
it, so there is no window where the running site is broken.

### 1. Database

Against **VData_Prod**, in order. Take a backup first. **Skip this if you already ran these scripts
for the 0809 bundle** — they are unchanged (both are idempotent, so re-running is harmless).

| File | What it does |
| --- | --- |
| `database\01-add-order-password-secret.sql` | Adds `Orders.PasswordSecret` and records the migration. Guarded by `__EFMigrationsHistory`. |
| `database\02-new-permissions.sql` | Creates the three new permission rows and (optionally) grants them. **Edit `@GrantToEmail` at the top first.** |

```powershell
sqlcmd -S <server> -d VData_Prod -U <user> -P <password> -C -b -i "database\01-add-order-password-secret.sql"
sqlcmd -S <server> -d VData_Prod -U <user> -P <password> -C -b -i "database\02-new-permissions.sql"
```

`-b` returns a non-zero exit code on error instead of carrying on quietly. Both were run twice
against a real database before shipping to confirm idempotency; `02` fails loudly if
`@GrantToEmail` matches no admin user.

> Assumes the database is at `20260802173703_AddAdminAttachedDocuments`. If it is further behind,
> generate a wider script: `dotnet ef migrations script <from> <to> --idempotent`.

### 2. API

```powershell
Stop-WebAppPool -Name "<your api pool>"
robocopy "<bundle>\api" E:\inetpub\DataVerification\api /MIR /XF web.config appsettings.Production.json
Start-WebAppPool -Name "<your api pool>"
```

Verify: <https://vdataapi.nen-global.org/swagger/index.html> lists `/api/v1/admin/settings/email`.

### 3. Web and Admin

`/XF web.config` **is** load-bearing here — the SPA `web.config` holds the rewrite rules and is not
part of the build, so without the flag `/MIR` deletes it and every deep link starts returning 404.

```powershell
robocopy "<bundle>\web"   E:\inetpub\DataVerification\web   /MIR /XF web.config
robocopy "<bundle>\admin" E:\inetpub\DataVerification\admin /MIR /XF web.config
```

Then **Ctrl+F5** once.

## After deploying

1. **Sign out and back in.** Permissions are baked into the token at login; an existing session will
   not have the new ones and the Settings page will show as read-only.
2. Open **Settings**. The amber banner should be gone.
3. Paste the SendGrid key and save. The status line changes to *Using the key set on this page*.
4. Register a test order and confirm the credentials email arrives.
5. Orders created **before** this deploy return `isAvailable: false, reason: "not_stored"` from the
   reveal endpoint. That is expected and permanent for them.

> Registration is rate-limited to **5 per 15 minutes per caller** (`RateLimiting:Registration` in
> `appsettings.json`). Repeated testing returns HTTP 429 and the form simply fails. Worth reviewing
> whether that limit suits real applicants behind a shared office IP or carrier NAT.

## Rollback

Redeploy the previous release over `api\`. The new column is nullable and the old build ignores it,
so no schema rollback is needed. The old build also ignores the stored SendGrid key and falls back
to `SendGrid__ApiKey` — make sure that is set before rolling back, or email stops.
